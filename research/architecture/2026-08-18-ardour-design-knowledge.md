# Ardour Design Knowledge — Findings Report

Design documentation only (ardour.org manual, ardour-dev mailing list archives, author interviews and essays). No C++ implementation read. All claims cited.

## 1. Region/source model

- **Source = file reference; Region = range into it.** "A region represents a single contiguous section of one or more media files," defined by: the source file(s), an **offset** (start point in the file) and a **length**; when placed in a playlist it gains a **position** and a **layer**. Regions are "cheap" (small memory/CPU), are never equivalent to files, and splitting/copying/trimming never alters or creates audio files — only recording, Export, Bounce and Reverse do. — [manual: working with regions](https://manual.ardour.org/working-with-regions/)
- **Layered overlaps**: the editing model is "layered" — multiple regions can stack at one location with arbitrary overlaps, so a crossfade cannot be an entity *between* two regions. Instead **each region carries its own crossfades at both ends**; the bottom-most region is rendered first, each region on top crossfading down onto the region(s) beneath it. Region fades *are* crossfades. — [manual: region fades and crossfades](https://manual.ardour.org/editing-and-arranging/create-region-fades-and-crossfades/)
- **Trimming** = changing region length, obeys snap; non-destructive. — [manual: change region lengths](https://manual.ardour.org/editing-and-arranging/change-region-lengths/)
- **Region gain/ramps**: constant region gain is an inherent, editable region property (boost/cut/normalize are non-destructive); the **gain envelope** is a per-region automation curve (control points) embedded in the region that travels with it on move/copy and is followed "continuously and accurately during playback." — [region gain](https://manual.ardour.org/editing/adjusting-gain/region-gain/), [gain envelopes](https://manual.ardour.org/editing/adjusting-gain/gain-envelopes/)
- **Trim/cut while playing**: the audio thread never reads regions directly — it only pulls from ring buffers filled by the butler on request, so playlist edits are decoupled from the process cycle and take effect at the next refill. — [ardour-dev 2005-11](http://lists.ardour.org/htdig.cgi/ardour-dev-ardour.org/2005-November/002802.html)
- **Non-sample-aligned granularity**: region positions were historically audio-time/sample-based; repeated musical↔audio conversions accumulate sub-sample errors that can put a note/region on the wrong sample, e.g. excluded from a loop/selection — the stated motivation for the nutempo redesign. — [interview with Paul Davis (2018)](https://www.admiralbumblebee.com/music/2018/02/20/Interview-with-Paul-Davis-of-Ardour-about-Ardour-6-and-more.html)

## 2. Disk streaming (butler thread)

- The JACK/audio process callback **pulls** samples from per-track ring buffers in order — transport position is implied by pull order; at playback start buffers are reset and refilled *before* the audio thread advances. A separate **"disk butler"** thread fills the ring buffers for all tracks: each track's Diskstream, at the butler's request, fills the next N samples by calling read() on its Playlist, which calls read() on the appropriate Region(s), which reference a file Source. — [ardour-dev 2005-11](http://lists.ardour.org/htdig.cgi/ardour-dev-ardour.org/2005-November/002802.html)
- Paul Davis (2013): the butler's purpose is "primarily to organize buffering within user space based on observed (but very occasional) delays in I/O" — it deliberately relies on kernel read-ahead. All files stay open (LRU cache of file descriptors for open-file limits); read-ahead is user-set (default **5 seconds**); writes are batched in **256 kB chunks** (from "very old" ext3 throughput experiments that predate libsndfile); repeated region reads are not optimized — the kernel buffer cache serves them (observed GB/s). — [LAD 2013-12](http://lalists.stanford.edu/lad/2013/12/0016.html)

## 3. Latency compensation (PDC)

- The manual explains the two strategies — **read-ahead** vs **write-behind** — and states Ardour uses **read-ahead**: the clock shows the audio as heard at the speakers, not where files are read from; when compensating, Ardour must read data from *before* the session start (timecode 01:00:00:00 case). — [manual: latency and latency compensation](https://manual.ardour.org/synchronization/latency-and-latency-compensation/)
- PDC was **retrofitted/redesigned in July 2005** ("the new PLC/alignment 'fixes' ('redesign' is perhaps more accurate)"): two **alignment styles** — "existing material" vs "exact capture time" — with a loopback-cable test methodology using an artificial-latency plugin; a commit log wryly lists "fix interaction of plugin latency compensation, alignment models input and output latencies and the phase of the moon," i.e. the known failure surface. — [ardour-dev 2005-07](http://lists.ardour.org/pipermail/ardour-dev-ardour.org/2005-July/002491.html)
- Failure modes documented: software monitoring adds round-trip latency (recommended: monitor via external hardware; A/D/A alone ≈1.5–2 ms); USB/FireWire interface latency is not constant and can change on reconnect/reboot/xruns, so recalibration is suggested. — [manual: latency considerations](https://manual.ardour.org/recording/monitoring/latency-considerations/)
- 13 years later, "Full latency compensation, everywhere, for everything" was still listed as a major Ardour 6.0 architectural change — i.e. PDC had persistent gaps. — [interview with Paul Davis (2018)](https://www.admiralbumblebee.com/music/2018/02/20/Interview-with-Paul-Davis-of-Ardour-about-Ardour-6-and-more.html)

## 4. Click-free transport/edits

- Every audio region has a fade-in and fade-out by default, "very short," whose explicit purpose "serves to de-click the transitions at the start and end of the region"; crossfades handle butted/overlapping regions; fades are automation-style curves, adjustable and non-destructive. — [manual: region fades and crossfades](https://manual.ardour.org/editing-and-arranging/create-region-fades-and-crossfades/)
- Gain envelope control points are interpolated continuously during playback (not stepped), so ramps are click-free. — [manual: gain envelopes](https://manual.ardour.org/editing/adjusting-gain/gain-envelopes/)

## 5. Session model & undo

- A Session is a **folder**: `name.ardour` (main snapshot) + `*.ardour` named snapshots, `name.ardour.bak` auto-backup, `name.history` (undo history), `instant.xml` (last zoom/metadata), `interchange/` (raw audio/MIDI), `peaks/`, `analysis/`, `dead sounds/`. Backward loading goes back to v2.8 (2009); unsupported data (e.g. "the old way of storing region fades") is skipped. — [manual: what's in a session](https://manual.ardour.org/working-with-sessions/whats-in-a-session/)
- Undo: all arrangement changes (regions, control points) are undoable; history is **saved to the session history file** so undo survives closing/quitting the session; separate limits for in-memory undo depth vs. history-file depth. — [manual: undo/redo](https://web.archive.org/web/20130612014550/http://www.manual.ardour.org/ardours-interface/basic-gui-operations/undoredo-for-editing-/)
- Undo scope is deliberately split: the main editor and the pianoroll have **separate undo histories**; pianoroll history is ephemeral (exists only while editing the same regions, never saved/restored) — an explicit design decision by Paul Davis. — [discourse: separate undo in the pianoroll](https://discourse.ardour.org/t/separate-undo-redo-history-in-the-pianoroll/113383)
- **Snapshots** = named frozen session versions; "Snapshot & keep working" vs "Snapshot & switch to new version" semantics; creating one never modifies the session. — [manual: snapshots](https://manual.ardour.org/working-with-sessions/snapshots/)

## 6. Clock/tempo

- Clock (speed; word clock at sample rate) is separated from time (position; timecode at video-frame granularity — e.g. 1920 samples/frame at 48 kHz/25 fps); JACK gives sample-accurate sync between apps. — [manual: on clock and time](https://manual.ardour.org/synchronization/on-clock-and-time/)
- TempoMap: tempo and time signature "belong together" — without both "there is no way to know where a beat lies in time." Tempo markers are **constant or ramped** (a ramp needs start+end tempos); each marker can be **audio-locked** (keeps frame position; its pulse moves) or **music-locked** (keeps pulse; frames move); time signatures are music-locked by default (must land on a bar line) unless audio-locked, which fixes the bar number — for rubato/film scoring. When tempo changes, timeline objects glued to bars/beats move in sympathy. — [manual: working with tempo and meter](https://manual.ardour.org/working-with-tempo-and-meter/)
- nutempo (Ardour 6): redesign so musical time is *not* converted to audio time "except when we absolutely have to, and to never convert back"; a **superclock** (high-resolution internal clock) does all tempo-map math to avoid rounding errors; a key insight: *durations need an associated position* (N beats → samples depends on where measured, since the tempo map may change); storing even audio time as superclock would make sample-rate changes "relatively trivial." — [interview with Paul Davis (2018)](https://www.admiralbumblebee.com/music/2018/02/20/Interview-with-Paul-Davis-of-Ardour-about-Ardour-6-and-more.html)
- Varispeed: the VS transport button sets a constant playback/record speed in semitones/cents/percent; whether it persists across stop is a preference ("Reset default speed on stop"); a shuttle speed control scrubs at 1.5× or 2× (acceleration multipliers). — [manual: the transport bar](https://manual.ardour.org/ardours-interface/the-transport-bar/)

## 7. Known debt / would-do-differently

- **PDC never became "complete"**: "Full latency compensation, everywhere, for everything" was an Ardour 6.0 goal (2018), 13 years after the first retrofit. — [interview with Paul Davis (2018)](https://www.admiralbumblebee.com/music/2018/02/20/Interview-with-Paul-Davis-of-Ardour-about-Ardour-6-and-more.html)
- **Time-domain conversion debt**: "The errors when converting between the two time domains are very small. Sub-sample small. The problems arise when we convert more than once… You can end up with a note on being on the wrong sample." — [interview with Paul Davis (2018)](https://www.admiralbumblebee.com/music/2018/02/20/Interview-with-Paul-Davis-of-Ardour-about-Ardour-6-and-more.html)
- **Legacy buffering decisions persist**: 256 kB write chunks from pre-libsndfile ext3 experiments; elaborate read-ahead strategies explicitly abandoned — "I'm not interested in the work involved in designing a better strategy," because kernel caching already streams 100 mono tracks from one cheap SATA disk. — [LAD 2013-12](http://lalists.stanford.edu/lad/2013/12/0016.html)
- **Redesign freedom vs. greenfield warning**: "If I decide some code I've written isn't good enough, I am free to rewrite it completely," yet his advice to newcomers is "Please don't start a new project!" — "I know I did [underestimate the work], by an amount measured in years." — [Linux Journal](https://www.linuxjournal.com/article/10295)
- **Session-format debt**: major releases change the session file format; back-compat is aimed for "when we can," but old data (e.g. region-fade storage) is dropped. — [manual: what's in a session](https://manual.ardour.org/working-with-sessions/whats-in-a-session/)

## Named mechanisms to carry into the Rust design

Source/Region/Playlist decomposition · layered regions with per-region end crossfades · butler thread + per-track ring buffers with pull-based transport position · read-ahead latency compensation · TempoMap with audio/music-locked markers · superclock-style internal time (no repeated musical↔audio conversion) · session folder + `.history` undo persistence · snapshot versions.
